# Troubleshooting

Common problems in day-to-day work with the repository and how to fix them.

## Merge conflict in `package-lock.json`

### Symptom

`git merge main` (or `git rebase main`, or a pull request on GitHub) reports:

```
CONFLICT (content): Merge conflict in package-lock.json
```

### Why it happens

`package-lock.json` is generated by npm. When two branches change dependencies or workspaces, both rewrite
the same parts of the file, even if the changes themselves do not overlap. For example, `main` added the
`mcp` workspace while a feature branch added `shared`.

### Fix

Do not edit the conflict markers in `package-lock.json` by hand and do not combine the two halves: the result is
easy to break and hard to review. Take one side as it is and let npm rebuild the rest from `package.json`.

1. Resolve all other conflicted files first, **`package.json` in particular**. npm builds the lock file from it,
   so it must already contain the changes of both sides (dependencies, `workspaces`, scripts).
2. Take the lock file from the branch you are merging in:

   ```bash
   git checkout --theirs package-lock.json
   ```

   During a **rebase** the sides are swapped (`ours` is the branch you rebase onto), so use
   `git checkout --ours package-lock.json` there.

3. Let npm add the changes of your branch (use Node 24, see `.nvmrc`):

   ```bash
   npm install
   ```

   Use `npm install`, not `npm ci`: `npm ci` refuses a lock file that does not match `package.json`.

4. Check what changed compared with the branch you merged in:

   ```bash
   git diff main -- package-lock.json
   ```

   Expect only the packages and workspaces your branch adds. If versions of unrelated packages changed,
   something went wrong; start again from step 2.

5. Mark the conflict as resolved, run the checks and finish the merge:

   ```bash
   git add package-lock.json
   npm run check
   git commit
   ```

   During a rebase use `git rebase --continue` instead of `git commit`.

### What not to do

- **Do not delete `package-lock.json` and regenerate it from scratch.** npm then picks the newest allowed
  version of every package, and the pull request suddenly upgrades dozens of dependencies.
- **Do not add `overrides` to `package.json`** to force versions. If versions drifted, go back to the lock file
  of `main` and run a plain `npm install`, as above.
- **Do not commit a lock file with conflict markers.** npm cannot read it, and CI fails at `npm ci`.
